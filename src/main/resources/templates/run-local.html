03Create the MySQL 8 databases — Workbench or automated installer

Both paths install the same ordered SQL scripts. Inspect the reset behavior before using it.

Two supported installation paths: Manual: inspect and execute individual SQL files using MySQL Workbench; Automated: let the repository’s database/install-db.sh apply all matching SQL scripts in filename order. Choose one path for a fresh installation; do not run both against an already populated database.

B. Automated installation using the actual install-db.sh

The supplied database/install-db.sh changes into its own directory and executes the glob sql/[0-9][0-9]_*.sql with the MySQL CLI, using utf8mb4. It accepts MYSQL_HOST, MYSQL_PORT, MYSQL_USER, and MYSQL_PWD; its defaults are localhost, 3306, root, and localroot.

TERMINAL · safe, first installation into a fresh local MySQL instance
cd /path/to/turfclub-erp
# Point MYSQL_HOST, MYSQL_PORT and MYSQL_USER at your lab instance if needed.
# Supply MYSQL_PWD in your shell environment (avoid putting real credentials in Git).
bash database/install-db.sh
Destructive reset (never use casually): bash database/install-db.sh --reset first drops the script’s 18 named Turf Club databases and then reapplies matching SQL files. This permanently destroys their existing data. It is appropriate only for an intentionally disposable local installation. The script’s reset list does not name chatbot; inspect any later-stage DDL separately before assuming a complete wipe of every schema.
TERMINAL · optional destructive reset, fresh throwaway lab ONLY
cd /path/to/turfclub-erp
# WARNING: permanently drops the 18 named Turf Club schemas and their data.
bash database/install-db.sh --reset

A. Recommended: fully offline historical generation

Start with a clean disposable local database that has just been installed via the manual or automated SQL path. seed-history.sh creates an isolated database/seed-history/.venv (if missing) and installs its own requirements.txt. Python 3.12 meets the script’s Python 3.10+ requirement. The script connects through the same MYSQL_* variables as install-db.sh.

TERMINAL · recommended installation order, run from ERP repository root
cd /path/to/turfclub-erp

# Database must be fresh and the 18+ SQL scripts installed already.
# Use the same MYSQL_HOST/MYSQL_PORT/MYSQL_USER/MYSQL_PWD
# environment as the database installer.

bash database/seed-history/seed-history.sh --offline

# Independent checks: the wrapper prints check failures but may continue.
database/seed-history/.venv/bin/python   database/seed-history/seed_history.py check
database/seed-history/.venv/bin/python   database/seed-history/seed_history.py report
Freshness prerequisite: seedgen/checks.py refuses normal phase 1 if the database already has more than four horses, any accounting events, or any wager tickets. Do not bypass this guard with --force merely to rerun a course setup. For a deliberately fresh lab, reset or recreate the appropriate database and rerun. A reset permanently deletes data.

The --offline option is meaningful: seedgen/offline.py recreates the GL posting and AR import logic directly against MySQL. It is designed for environments without running ERP services; it does not execute their HTTP endpoints or exercise their live outbox relays. It is appropriate for preparing realistic training data before Keycloak.

Optional deterministic variation and resume controls

TERMINAL · documented shell options
# Generate an alternative repeatable business history, scaling horses and members:
bash database/seed-history/seed-history.sh --offline   --seed 20261114 --today 2026-11-24 --scale 1.0

# Recovery: only after earlier steps completed and run state exists.
bash database/seed-history/seed-history.sh --offline --from phase2

# Supported resume names:
# phase1 | post1 | phase2 | post2 | phase3 | checks

--today sets the simulated installation date, defaulting to the current venue date in America/Chicago. The normal window is 364 days before that date through the day before it. The command does not create historical Keycloak users; it labels MySQL audit records with the simulated application actor names.

Validation gate—before creating the Keycloak realm

The generator reports horses, meetings, official races, tickets, POS orders, invoices, receipts, posted GL journals, bank transactions, reconciliations, audit events, outbox status, AR backlog and trial balance. validate.py tests rules such as ownership totaling 100%, valid licensed runners, correct wagers and payouts, nonnegative stock, completed reconciliations, fully posted accounting events and a balanced GL.

MYSQL WORKBENCH · inspect the populated enterprise

Check failures must be investigated: the wrapper uses seed_history.py check || echo ..., so the shell script can finish and print a report even if some business-rule checks fail. Run seed_history.py check independently as shown above and require exit status zero before proceeding. Also inspect the outbox for any FAILED records.
Offline completion gate: SQL scripts applied, historical phases finished, outbox and AR processing complete, validation passes, and the trial balance totals zero. You can now configure Keycloak, build, and start the ERP for the first time.

B. Alternative: online seed mode using real Spring Boot outbox relays

This route uses a different sequence. Without --offline, the wrapper needs the built JARs and the turfclub Keycloak realm. It performs phase 1 while services are stopped, then starts scripts/run-all.sh with faster outbox processing to post the generated events, imports AR, runs phases 2 and 3, and leaves the services running. Choose it only when you explicitly want to demonstrate the actual Java relay processing.

TERMINAL · alternative online mode, after Keycloak and Maven build
cd /path/to/turfclub-erp
# Requires a fresh database, configured Keycloak realm on :8080,
# successfully built Java JARs, and all ERP services STOPPED for phase 1.
bash database/seed-history/seed-history.sh

# When the script completes, it leaves the services running.
# Restart with normal relay settings if desired:
bash scripts/run-all.sh stop
bash scripts/run-all.sh

For online mode, the script checks localhost:8102/actuator/health, increases MySQL max_connections to 500 when below 400, and uses fast-relay Java options (turfclub.outbox.batch-size=500, turfclub.outbox.poll-ms=250, turfclub.ar.import-ms=2000). MySQL needs sufficient privileges to run SET GLOBAL max_connections. Its change is temporary unless made persistent in MySQL configuration.

What both paths teach: Business activities create operational records and accounting events. Those events ultimately become GL journals and AR obligations; customer payments then feed treasury and reconciliation. Offline mode prepares a repeatable lab; online mode exercises the real asynchronous Java integration behavior.

05Configure Keycloak 26 and the ERP realm

Authentication, sessions and service authorization must be configured before opening protected ERP pages.

Start the Keycloak 26 server using its documented development-startup procedure and create the local administrator account.
Open the Keycloak administration console and create/import the turfclub realm. Prefer importing the repository-provided realm JSON, if available.
Verify the ERP's OIDC client registrations, redirect URIs, browser flow, service accounts, client scopes, realm roles and application roles.
Ensure that application issuer URLs, client IDs, database credentials, and other local environment settings match the actual repository configuration.
Test an authorized account and a restricted account to illustrate identity verification versus business authorization.
TERMINAL · optional OIDC metadata check, for local port 8080
curl -fsS http://localhost:8080/realms/turfclub/.well-known/openid-configuration

The URL above assumes Keycloak is configured on HTTP port 8080 with realm turfclub. If your setup uses HTTPS, a reverse proxy or a different port, use its configured issuer URL instead. Never copy production client secrets into a public repository.

Important: Use the checked-in realm-export and current client configuration from your checkout. Do not invent missing clients or credentials; use the checked-in realm definition and application settings.

06Build the complete Java ERP with one Maven command

The root pom.xml is an existing Maven aggregator. There is no need for a separate build-all shell script.

Verified on the source project: the Maven reactor completed all 16 projects successfully—root aggregator, shared library, and 14 Spring Boot services—with BUILD SUCCESS in 26.220 seconds on the author's Mac (14 November 2026).
TERMINAL · run from the turfclub-erp repository root
mvn clean install -DskipTests

Maven compiles the common module first, resolves the other projects in dependency order, packages the executable Spring Boot JARs, and installs artifacts into the local Maven repository.

16 / 16 SUCCESS1 aggregator + 1 common JAR + 14 Spring Boot JARs

-DskipTests skips running tests; a successful build does not prove database connections, SSO, or the runtime health of every service. For a full validation build, run your project tests separately.

07Start the applications with the repository script

After building the project, run the repository's shared application launcher rather than opening fourteen separate terminals.

Before you start: MySQL must be running, all required schemas and historical seed-generation phases must be complete and validated, and Keycloak must be available at the issuer URL expected by your applications. Check local credentials and port assignments.
TERMINAL · from the turfclub-erp repository root
# Review the actual script before first execution
sed -n '1,240p' scripts/run-all.sh

# Start using the existing repository entry point
bash scripts/run-all.sh

What the launcher should accomplish: start the fourteen Spring Boot services with the correct environment, make their logs available, and report startup failures clearly. The script's exact behavior—foreground or background processes, log paths, shutdown support and health checks—depends on its current implementation and is not assumed here.

Why the commands are separate: mvn clean install compiles and packages software; run-all.sh starts processes. Keeping these responsibilities separate avoids rebuilding everything for each application restart.

10Resolve common local startup problems

A successful Maven build does not automatically establish that MySQL, Keycloak, or all fourteen application processes are healthy.

Check java -version and mvn -version; both must use the installed Java 21 JDK. Revisit JAVA_HOME and your shell's PATH.

Confirm MySQL is running, test credentials in Workbench, check datasource environment settings, verify all required schema scripts were executed in dependency order, and review missing-reference foreign key errors.

Check the Keycloak realm's issuer URL, client ID, redirect URI, port, role mappings and server logs. OIDC discovery should be reachable, and application configurations must agree with the realm issuer.

Use lsof -nP -iTCP:8101 -sTCP:LISTEN to identify the listener on port 8101; substitute the affected port. Inspect processes before stopping anything, and use the launcher’s supported shutdown procedure if provided.

Read the affected service's logs for the first root-cause exception. Typical causes include datasource authentication, schema mismatch, Keycloak discovery, unresolved environment variables, and conflicts with an existing process.
TERMINAL · quick local checks (macOS)
# Check which expected service ports are listening
for port in $(seq 8101 8114); do
  if lsof -nP -iTCP:$port -sTCP:LISTEN >/dev/null 2>&1; then
    echo "$port : LISTENING"
  else
    echo "$port : NOT LISTENING"
  fi
done

# Inspect a specific port if necessary
lsof -nP -iTCP:8101 -sTCP:LISTEN

A LISTENING result shows that something is bound to that port. It does not establish successful authentication, REST behavior, database connectivity, or application readiness.
